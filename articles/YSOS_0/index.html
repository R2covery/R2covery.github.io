Rust编程实验

使用 Rust 编写一个程序，完成以下任务：

a.创建一个函数 count_down(seconds: u64)

该函数接收一个 u64 类型的参数，表示倒计时的秒数。

函数应该每秒输出剩余的秒数，直到倒计时结束，然后输出 Countdown finished!。

b. 创建一个函数 read_and_print(file_path: &str)

该函数接收一个字符串参数，表示文件的路径。

函数应该尝试读取并输出文件的内容。如果文件不存在，函数应该使用 expect 方法主动 panic，并输出 File not found!。

c. 创建一个函数 file_size(file_path: &str) -> Result<u64, &str>

该函数接收一个字符串参数，表示文件的路径，并返回一个 Result。

函数应该尝试打开文件，并在 Result 中返回文件大小。如果文件不存在，函数应该返回一个包含 File not found! 字符串的 Err。

d. 在 main 函数中，按照如下顺序调用上述函数：

首先调用 count_down(5) 函数进行倒计时
然后调用 read_and_print(“/etc/hosts”) 函数尝试读取并输出文件内容
最后使用 std::io 获取几个用户输入的路径，并调用 file_size 函数尝试获取文件大小，并处理可能的错误。

实现函数 humanized_size(size: u64) -> (f64, &'static str)将字节数转换为人类可读的大小和单位

使用 1024 进制，并使用二进制前缀 （B, KiB, MiB, GiB）作为单位

实现一个元组结构体 UniqueId(u16)

使得每次调用 UniqueId::new() 时总会得到一个新的不重复的 UniqueId。

AtomicU16: 我们使用 AtomicU16 来存储当前的 ID 值。AtomicU16 是一个原子类型，可以在多线程环境下安全地进行操作。

fetch_add: 每次调用 new() 时，我们使用 fetch_add 方法来原子地增加 COUNTER 的值，并返回增加前的值。fetch_add 保证了即使在多线程环境下，每个线程都会得到一个唯一的 ID。

Ordering::Relaxed: 我们使用 Ordering::Relaxed 来指定内存顺序。在这个简单的场景下，Relaxed 顺序已经足够，因为我们只需要保证 COUNTER 的递增是原子的。

UniqueId 结构体: UniqueId 是一个简单的元组结构体，包含一个 u16 类型的字段。

初始化仓库

使用 QEMU 启动 UEFI Shell

图中包括了：

  1. 启动命令：

    • qemu - system - x86_64 - bios./assets/OVMF.fd - net none - nographic：这是用于启动QEMU模拟器的命令。其中，qemu - system - x86_64指定了QEMU模拟的目标平台为x86_64架构；- bios./assets/OVMF.fd指定了使用的UEFI固件文件为 OVMF.fd；- net none表示不启用网络功能；- nographic表示以非图形化模式运行。

  2. UEFI信息：

    • UEFI Interactive Shell v2.2：表明当前进入的是UEFI交互式外壳，版本为2.2。
    • EDK II：这是用于开发UEFI固件的一个平台，即EFI开发套件II（EFI Development Kit II）。
    • UEFI v2.70 (EDK II, 0x00010000)：显示了UEFI的版本为2.70，基于EDK II开发。

  3. 映射表（Mapping table）：

    • BLK0: Alias(s):：表示一个块设备的别名信息。
    • PciRoot(0x0)/Pci(0x1,0x1)/Ata(0x0)：这是块设备在PCI层次结构中的路径，表示该设备连接在PCI根总线的0号设备、1号功能下的ATA接口上。

  4. 启动提示：

    • Press ESC in 1 seconds to skip startup.nsh or any other key to continue.：提示用户在1秒内按下ESC键可以跳过名为 startup.nsh的脚本，否则按任意键继续。

  5. Shell提示符：

    • Shell>：这是UEFI交互式外壳的命令提示符，用户可以在此输入各种UEFI shell命令来进行操作，例如查看文件系统、管理设备等。

这说明在QEMU模拟器中成功启动了基于EDK II的UEFI系统，并进入了UEFI交互式外壳环境，以在此进一步进行系统相关的操作和配置。

启动YSOS

配置 Rust Toolchain

仓库提供的 rust-toolchain.toml 文件指定了需要使用的 Rust 工具链版本

具体来说，为了编译 UEFI 程序，我们需要使用 x86_64-unknown-uefi 编译目标。

同时，我们需要使用 rust-src 组件来编译标准库，使用 rustfmt 组件来格式化代码，使用 clippy 组件来获取一些代码编写建议。

为了编译内核和启用一些面向裸机的特性，我们需要使用 nightly 版本的 Rust 工具链。

在配置好的工作区中执行编译时，Rust 会自动下载并安装对应的工具链。

运行第一个 UEFI 程序

编译一个 UEFI 程序时，我们没有操作系统所提供的标准库，也没有操作系统提供的 Interpreter，因此我们需要使用 #![no_std] 来声明我们的程序不依赖标准库，使用 #![no_main] 来声明我们的程序不依赖操作系统的入口函数。

同时，我们需要使用 core 和 alloc crate 来提供一些基本的数据结构和功能，使用 uefi crate 来提供 UEFI 程序运行时所需要的各种信息。

具体而言，efi_main 通过 #[entry] 被指定为 UEFI 程序的入口函数，在 efi_main 函数中，首先对 UEFI 相关功能组件进行初始化，然后进入一个死循环，每次循环输出一条日志后等待一段时间。

思考题

了解现代操作系统（Windows）的启动过程，UEFI 和 Legacy（BIOS）的区别是什么？

现代操作系统（Windows）的启动过程

BIOS/UEFI阶段：计算机通电后，BIOS或UEFI进行硬件初始化，执行加电自检（POST），检查硬件是否正常工作。之后查找启动设备（通常是硬盘），将操作系统的引导加载程序（Windows Boot Manager）加载到内存。

Windows Boot Manager阶段：负责显示引导菜单，允许用户选择启动项，如不同版本的Windows或其他操作系统。用户选择后，Boot Manager加载选定操作系统的启动加载程序。

启动加载程序阶段：启动加载程序（如Winload.exe）被加载到内存，它负责加载Windows内核。

Windows内核加载阶段：Windows内核（ntoskrnl.exe）被加载到内存中，内核初始化系统组件，建立内存管理、设备驱动程序等，并创建会话管理器进程（Winlogon.exe）。

会话管理器启动阶段：会话管理器（Winlogon.exe）负责用户登录，显示登录界面，用户输入凭据后，Winlogon验证用户身份，加载用户配置文件。

用户登录阶段：用户配置文件包括用户的桌面设置、程序启动项等，并启动用户级别的进程，如系统托盘、网络连接等。

资源管理器启动阶段：Windows资源管理器（Explorer.exe）启动，负责加载桌面、任务栏、桌面图标等用户界面元素。

用户桌面显示阶段：最终，用户桌面显示，用户可以开始使用计算机。

UEFI和Legacy（BIOS）的区别

  1. 基础架构：

    • Legacy（BIOS）：是最早的一种固件接口，在计算机开机时初始化和测试系统硬件，并加载操作系统。
    • UEFI：是一种个人电脑系统规格，用来定义操作系统与系统固件之间的软件界面，作为BIOS的替代方案，提供了更多更现代的功能。

  2. 启动方式：

    • Legacy（BIOS）：采用MBR（主引导记录）方式启动，每个磁盘只能有一个活动分区。
    • UEFI：采用GPT（GUID分区表）方式启动，每个磁盘可以有多个启动分区。

  3. 支持硬盘容量：

    • Legacy（BIOS）：因采用MBR分区方式，对硬盘大小有限制，最大支持2TB。
    • UEFI：采用GPT分区方式，理论上可支持高达18EB的硬盘大小。

  4. 安全性：

    • Legacy（BIOS）：没有安全启动功能。
    • UEFI：提供了“安全启动”功能，可防止未授权的操作系统和软件启动。

  5. 兼容性：

    • Legacy（BIOS）：兼容性较强，支持所有Windows系统的安装，但只支持32位硬件和操作系统。
    • UEFI：支持64位的硬件和操作系统，不过UEFI启动模式下不支持XP、部分Win7系统的安装（如需安装不仅要将UEFI启动模式更改为传统启动模式，还需将硬盘分区模式更改为MBR分区，且部分新电脑强制安装会出现USB接口失灵现象 ）。

  6. 启动速度：

    • Legacy（BIOS）：启动过程相对繁琐，效率低，开机速度慢。
    • UEFI：使开机程序化繁为简，能加快启动速度，提高开机后操作系统的启动速度。

尝试解释 Makefile 中的命令做了哪些事情？

这个 Makefile 主要用于构建和运行一个基于 UEFI 的操作系统或引导程序（ysos_boot）。它定义了一些目标（targets）和变量，用于编译代码、设置 QEMU 虚拟机环境以及运行调试。

变量定义

  • OVMF: 指定 OVMF（UEFI 固件）文件的路径，用于 QEMU 启动。
  • ESP: 指定 EFI 系统分区（ESP）的目录名称，用于存放 UEFI 可执行文件。
  • BUILD_ARGS: 构建参数，默认为空。如果 MODE=release，则设置为 --release。
  • QEMU_ARGS: QEMU 的额外参数，例如 -m 64M 设置虚拟机内存为 64MB。
  • QEMU_OUTPUT: QEMU 的输出模式，-nographic 表示禁用图形界面。
  • MODE: 构建模式，默认为 release。可以通过命令行覆盖，例如 make MODE=debug。
  • CUR_PATH: 当前路径，通过 $(shell pwd) 获取。
  • DBG_INFO: 调试信息标志，当前未使用。

条件判断

  • 如果 MODE 是 release，则设置 BUILD_ARGS 为 --release，表示以发布模式构建。

目标定义

run

  • 依赖 build 和 launch 目标。
  • 先构建项目，然后启动 QEMU。

launch

  • 启动 QEMU 虚拟机。
  • -bios ${OVMF}: 使用指定的 OVMF 固件。
  • -net none: 禁用网络。
  • $(QEMU_ARGS): 添加额外的 QEMU 参数（如内存大小）。
  • $(QEMU_OUTPUT): 设置输出模式（如 -nographic）。
  • -drive format=raw,file=fat:${ESP}: 将 esp 目录作为 FAT 格式的虚拟磁盘加载。
  • -snapshot: 以快照模式运行，避免对虚拟磁盘的修改。

intdbg

  • 启动 QEMU 并启用中断调试。
  • -no-reboot: 虚拟机退出时不重启。
  • -d int,cpu_reset: 启用中断和 CPU 重置的调试信息。

debug

  • 启动 QEMU 并等待 GDB 连接。
  • -s: 启用 GDB 调试，监听端口 1234。
  • -S: 启动时不运行 CPU，等待 GDB 连接。

clean

  • 清理构建产物，调用 cargo clean 删除 target 目录。

build

  • 依赖 $(ESP) 目标，表示构建项目并准备 ESP 目录。

$(ESP)

  • 依赖 $(ESP)/EFI/BOOT/BOOTX64.EFI 目标，表示需要将构建的 EFI 文件复制到 ESP 目录。

$(ESP)/EFI/BOOT/BOOTX64.EFI

  • 将构建的 ysos_boot.efi 文件复制到 ESP 目录的 EFI/BOOT/BOOTX64.EFI 路径。
  • mkdir -p $(@D): 创建目标目录（如果不存在）。
  • cp $< $@: 复制文件，$< 是第一个依赖项（ysos_boot.efi），$@ 是目标文件（BOOTX64.EFI）。

target/x86_64-unknown-uefi/$(MODE)/ysos_boot.efi

  • 构建 ysos_boot.efi 文件。
  • cd pkg/boot && cargo build $(BUILD_ARGS): 进入 pkg/boot 目录并调用 cargo build，根据 BUILD_ARGS 决定是否以发布模式构建。

总结

这个 Makefile 的主要功能是：

  1. 构建 UEFI 引导程序：通过 cargo build 构建 ysos_boot.efi。
  2. 准备 ESP 目录：将构建的 EFI 文件复制到 ESP 目录的指定路径。
  3. 启动 QEMU：使用 OVMF 固件和 ESP 目录启动虚拟机，支持普通运行、调试和中断调试。
  4. 清理构建产物：通过 cargo clean 清理构建文件。

利用 cargo 的包管理和 docs.rs 的文档，我们可以很方便的使用第三方库。这些库的源代码在哪里？它们是什么时候被编译的？

在Rust生态中，使用 cargo管理的第三方库，其源代码通常存储在 crates.io仓库（这是Rust官方的包仓库 ）。

程序运行时编译。当使用 cargo构建项目并编译依赖库时，编译时间是构建过程中的一个瞬时信息，通常在构建日志中可以看到某个库具体开始编译和结束编译的时间点。但这些日志信息在构建完成后一般不会持久保存特定的编译时间记录。

为什么需要用 #[entry] 而不是直接使用 main 函数作为程序的入口？

（生成自Kimi）

在Rust中使用 #[entry]而非直接用 main函数作为程序入口，主要有以下一些原因：

底层控制和定制化启动流程

在一些特殊场景下，比如嵌入式开发等，开发者可能需要对程序的启动过程进行更精细的控制。#[entry]可以让开发者绕过Rust默认的一些启动设置，直接定义程序最开始执行的代码逻辑。例如，在嵌入式系统中，可能需要在初始化硬件（如设置时钟、配置外设等）之后再进入业务逻辑代码，通过 #[entry]可以将这些初始化代码放在入口函数中，确保在任何其他代码执行之前先完成硬件相关的准备工作。

与裸机编程等场景适配

当进行裸机编程（即不依赖操作系统的编程，直接在硬件上运行程序）时，Rust默认的 main函数入口机制可能无法满足需求。因为裸机环境下没有操作系统提供的各种运行时支持，#[entry]允许开发者编写符合裸机启动要求的代码，实现从硬件启动到程序执行的完整流程。

构建特定类型的程序

对于一些需要构建启动器、引导程序等特殊用途程序的场景，#[entry]提供了更灵活的入口定义方式。可以根据这类程序的独特需求，定制启动逻辑，而不是局限于 main函数默认的启动行为。

与标准库的解耦

使用 #[entry]还可以在一定程度上实现与标准库的解耦。在一些对程序体积、运行环境有严格要求的场景下，标准库可能并不是必需的或者甚至是不适用的。通过 #[entry]定义入口函数，可以在不依赖标准库中与 main函数相关的启动代码的情况下，编写独立运行的程序。
